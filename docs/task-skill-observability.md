# Local task and skill observations

The Pi extension records allowlisted observations as session custom entries. It does not decide task completion, board claims, dispatch, or review authority. Session reports remain local. An explicit-input, read-only cross-session count CLI is available; it is not a scheduler, network export, model comparison or independent verifier. Session custom entries reuse an evidence-entry pattern, not the driver's recovery-evidence store. This is local instrumentation preparation, not completion of the fleet-evaluation goal.

## Release is not an inert rollout

Pi package settings can discover extensions through a directory plus a denylist. If this extension is not denied, installing a release auto-registers its hooks and model-callable tool in each fresh session. There is no separate opt-in gate here. A release/install would therefore activate observation globally on that setup; source edits or private validation do not activate it. No install, release, public sync or host-settings change is approved by this work. Owner awareness and separate rollout approval remain necessary; do not describe the published observer as activation-deferred.

A successful `TaskCreate` starts a pending attempt; a successful transition to `in_progress` starts it. On resume, the existing attempt is restored and a `resume-boundary` capture gap is recorded. A successful, matching `TaskUpdate` status transition to `completed` or `deleted` ends task-local attribution, including in-flight calls whose results arrive later; it does **not** establish a verified success or create a reported outcome. Failed updates, unchanged status, and another task's terminal transition do not close the active task. On resume a terminal task is not restored. A later attempt needs a real new status transition or a distinct caller-declared worker attempt. Replayed task starts and duplicate event IDs do not create extra attempts. An observation outcome also closes the observed active attempt; a conflicting second outcome is refused. Session and task reports group by session, task, internal worker partition and attempt, not by skill name alone. Outside a pane the automatic partition has `workerId: null` and `workerIdentityProvenance: not-captured`. When the three named Herdr pane, tab and workspace environment values agree, the observer stores only a hashed pane ID with `herdr-pane-observed` provenance. A successful coordinator spawn result stores its returned pane ID hash and validated role separately. The aggregate attributes that role only if the worker-side observed pane matches exactly one coordinator role; conflicting or absent spawn records leave the role uncaptured. A caller-supplied worker ID remains `caller-declared`. No role is inferred from a name or from a pane environment variable. Existing stored partition hashes are not rewritten. A task without a captured recipe has unknown requirements.

Call `agentic_task_skill_observation` with `kind: recipe` to declare `recipe`, `source: pi-poteto-mode`, numeric `version`, `requiredSkills`, and numbered `requiredSteps`. This is **caller-declared provenance**, not a verified manifest or independently resolved playbook. Equivalent repeated declarations stay caller-declared. Conflicting recipe/source/version/requirement sets yield no selected recipe, `requirementsProvenance: conflicting-caller-declarations`, `coverage: requirements-conflicting` and a separate conflict total; the first declaration does not silently win. The observer cannot establish actual recipe requirements or identify a better recipe. Use `kind: activity` with `declared`, `step`, or `skip`, and `kind: outcome` for a reported outcome. `kind: report` or `/skill-observation-report` returns the local summary. A worker without an active Pi task must supply task, attempt and worker IDs; these links remain caller assertions.

A successful read of an allowlisted `pi-poteto-mode/skills/<name>-pi/SKILL.md` under `PI_POTETO_SKILLS_ROOT`, or the conventional `pi-poteto-mode/skills` directory below the current user's home when unset counts only as a read. The observer does not inventory available skills. Playbook files, references, and reads under other skill roots are not counted; `captureLimits` lists `availability-inventory-not-captured`, `playbook-and-reference-reads-not-captured`, `other-skill-roots-not-captured`, `pre-observer-history-not-captured`, `role-without-matched-spawn-not-captured`, `skill-command-expansion-and-use-not-verified` and `cross-session-input-may-be-incomplete` on both empty and populated session or task reports. Only successful tool-based leaf reads count as loads. The Pi `input` event records an allowlisted `/skill:name` submitted during an active task as `command-submitted`; it stores neither arguments nor raw input. This proves submission before expansion, not expansion or skill use. A zero read or submitted-command count does not prove that no skill was used, or that the extension was loaded before the task. Alternate layouts require explicit root configuration; this change does not alter host settings. `available: not-captured` remains unmeasured even after a successful read. The pre-observer limit identifies an unobservable history window, not proof an earlier read or crash occurred. A step needs an explicit skill declaration and a successful, observed **work** tool reference from the same attempt. Reads, observer tool calls, another task's tool calls, failures, and arbitrary references cannot supply step evidence. Even a cited successful work call does not prove that the skill was used correctly. A skipped required step remains skipped; an absent one remains missing. A model-reported success is `reportedOutcome: success`, while `outcome` remains `unknown`. The legacy `reason: verified-result` input is accepted for compatibility but projected to `reportedReason: caller-reported-result`, whether the entry is new or already stored. Existing session entries are not rewritten. A cited successful work call is still not verification of a skill or task result. No reported success or caller-declared requirements can set `compliant: true`. A matching observed failed work call may substantiate a failure report. Capture gaps, absent metadata, and conflicting outcomes stay conservative. The version-one observer has **no independent success verifier**.

`parentTaskId` and `dispatchId` are optional caller assertions. A null link with `parentTaskLinkProvenance` or `dispatchLinkProvenance` set to `not-asserted` does not mean there is no parent or dispatch. A single asserted link is labeled `caller-declared`; conflicting declarations are labeled `conflicting-caller-declarations` and yield a null link. Neither label proves dispatch origin. The recipe name and semver-shaped version also remain caller-declared, not verified against a manifest. `resume-boundary` records a return to the attempt, not crash detection; an attempt that never resumes remains unknown.

Stored identifiers and call references are SHA-256 projections of bounded inputs; recipe names, skill names, step numbers, reasons, and versions use closed fields. No raw identifier, prompt, path, tool argument, result body, explanation, or transcript is appended by this observer. Hashes correlate events but are not secret encryption and do not authenticate caller claims. Normal Pi session files may contain ordinary transcripts outside these custom entries; normal session retention and export behavior still applies. Observation history cannot be reconstructed if the extension was not loaded, and a resume boundary does not prove a crash.

## Explicit-input aggregate

Run `node scripts/task_skill_observation_report.mjs <session.jsonl>...` or pass an explicit directory containing session JSONL files. No default path or home scan is performed. Only custom entries with the observer's type are parsed; replayed session/event IDs count once. Output contains deterministic counts by recipe, skill loads and submitted commands, matched role where observed, outcome and reason. Every report carries the capture limits. A successful command submission is not skill use, an unknown outcome is not success, and a count does not imply causality. The CLI reads local files only and exports no data. Files outside the explicit input, missing observer history, conflicting roles and independent result verification remain uncaptured. Normal Pi session files still have their ordinary retention policy. The CLI is a read-only local view, not a fleet store.
