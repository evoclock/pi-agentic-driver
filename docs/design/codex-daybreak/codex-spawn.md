# Codex worker spawn (independent draft)

Herdr 0.9.1 `agent start --help` lists `--kind codex` and positional agent arguments, but **does not allow a custom executable**: `--kind` selects the canonical executable. `tab create --help` does offer `--env KEY=VALUE` for the launched process. Rather than shadow `codex` in PATH with a wrapper or assume the Herdr CLI client's environment reaches a server-owned terminal, PAD owns the configured launch policy: add only the selected `CODEX_HOME` as tab environment, then start canonical `codex` with `-m` and the account's explicit `-c daybreak=true` or `-c daybreak=false` value. This is the supported launcher route, not a shell command or user-controlled argv.

The owner supplies paths (not credentials) in the active Pi profile's `codex-accounts.v1.json` (example in `config/`). In root mode, the top-level binaryRealRoot is a canonical directory and binaryLaunchPath is the exact absolute owner-selected stable launcher alias; the resolved binary must sit strictly beneath the root at precisely one release directory followed by bin/codex. A new release can replace the alias target without changing the config. Alternatively, binaryRealPath is an absolute canonical exact target, which remains valid without a root but requires an owner edit when its versioned location changes. If both an alias and a root are configured, binaryRealPath is not required. A missing path, traversal spelling, symlink escape, unconfigured alias, or wrong executable shape refuses. This is an owner step after the released PAD package update; bots never write the active account map.

Owner-only path example (replace the placeholder home with the owner-selected canonical home; no credentials):

    {
      "schema": "pad.codex-accounts.v1",
      "accounts": { "acct-a": { "home": "<ACCOUNT_HOME>", "model": "<MODEL_ID>", "daybreak": false } },
      "binaryLaunchPath": "<OWNER_BINARY_LAUNCH_PATH>",
      "binaryRealRoot": "<OWNER_BINARY_RELEASE_ROOT>"
    }

An absent, relative, symlinked canonical target or mismatched launcher alias refuses before tab creation. Each account entry declares its own canonical home, model and boolean Daybreak value; no account name or model is selected by the repository. Do not use a shared Pi login folder or symlinked homes. Paths must exist, be canonical, owned by the current user and not group- or world-writable; the account map must meet the same owner and write-bit checks. Codex skips `resolveInstalledModel`, including the Pi-installed-model roster, model-route-policy and budget controls: only the validated local account/model map and explicit account-scoped grant apply. Missing paths, unconfigured accounts/models and absent kind/account grants are denied before creating a tab. Account-map provisioning and live process observation remain separate, unverified owner-controlled work.

The example JSON contains only synthetic account identifiers and placeholder paths. Account provisioning and login are owner-only work; nothing here creates folders or logs in automatically.

The launch readbacks must match kind, role, pane, repository, fixed args, the configured binary identity rule and the real process's `CODEX_HOME` / model / Daybreak flag. The process argv0 must equal an explicitly configured binaryLaunchPath or binaryRealPath; in root mode its resolved target must sit strictly inside binaryRealRoot at one release directory/bin/codex, and it must be executable with a native Mach-O header; an unqualified codex argv0, PATH-shadowed executable, shell script, relative path, or non-executable file is refused. Real PID executable identity and binary immutability are not proven by argv alone. `agent get` must expose a PID. On macOS, the bundled short-lived Python standard-library helper reads KERN_PROCARGS2 for that PID and emits only the CODEX_HOME value; the adapter separately reads argv without environment mode and accepts exactly the fixed launch args. If the system Python or helper is absent, it refuses **before tab creation**. An unavailable PID or mismatched facts after an agent start return an `agent_started` **partial**, labelled uncertified and not usable. No raw process environment is returned or logged by the helper. The OS reader and exact `agent get` PID shape have not been verified in a live owner-provisioned environment; no real worker was started here. Existing partial lifecycle never automatically closes or retries a live agent.

`agentic_herdr_communication` refuses Codex prompts until role-bound kind/account/PID/model/Daybreak attestation can be independently rechecked; it currently has no such receipt. If a Pi role changes to Codex on the second observation, one pre-prompt terminal read may already have occurred between the two observations. No prompt is sent after the kind change. Pi role mapping, bounded Herdr prompt/read and report markers are unchanged. This draft does not alter the workflow runner track. Fleet-guard (outside this repository) still needs the exact change stated in the PR body before a live Codex worker can be eligible.

The bash guard's raw Herdr shell pattern has an older trailing-boundary gap for `herdr;ls`; it predates this PR and is not addressed by this Codex-scoped change. R5-3's name-only gap is tightened by the configured exact path or release-root and native-binary check, but real PID identity and time-of-check/time-of-use remain unverified. AJ-4's re-prompt-after-unknown-delivery path and DispatchReprompt are unchanged.

## Current setup

This ships as an interim route for a configured setup: an owner, Pi and Codex. It is not the general design. The PAD MCP server is the planned general entry point.
