# Daybreak Blue on Pi

The repository Pi SDK devDependencies supply `@earendil-works/pi-ai` and `@earendil-works/pi-coding-agent`. The Codex Responses provider calls `options.onPayload(body, model)` before serializing/sending the body (SSE or WebSocket). Pi exposes that option through `before_provider_request` (`pi-coding-agent/dist/core/sdk.js`, `docs/extensions.md`). No installed package is patched.

The automatically loaded PAD extension `extensions/daybreak-blue.ts` uses the outgoing **request body's** model, not `ctx.model`, which can be a virtual/router model. It sets `access_programs.cyber = "daybreak_blue"` only on a Codex Responses-shaped `the configured model` body, and strips inherited `cyber` on all other bodies, including `the configured model` and malformed requests. This shape check is a heuristic: the hook cannot see the resolved provider identity. As of pi-ai 1.5.2, OpenAI/Azure Responses providers omit the `instructions` field and so fail this check; a future provider or extension adding those fields could match erroneously. The handler strips any `access_programs.cyber` value from nonmatching bodies, not only Daybreak Blue. Pi swallows hook errors, so the handler returns a sanitized body rather than throwing. An invalid/non-object payload cannot be sanitized here; provider-level interception would be needed for a true fail-closed guarantee.

**Guard / unsupported requests:** Pi compaction, turn-prefix, and branch-summary streams do not pass `onPayload` through this extension hook. The extension cannot claim or verify Daybreak coverage for those requests; do not rely on Daybreak for them. A supported Pi provider-level hook is needed before advertising complete coverage. A later `before_provider_request` handler may override our body and reintroduce `cyber` or remove it; there is no supported post-handler request hook to enforce ordering. Treat later-handler interference as a live-pending risk and inspect extension load order before relying on this setting.

`node --test tests/test_daybreak_blue.mjs` uses synthetic credentials and a fake HTTP transport on the repository Pi SDK devDependency (the Pi CLI bundles equivalent provider code) to inspect the actual serialized outgoing request. It deliberately injects an earlier Daybreak value on the standard model and checks its removal. Both fake-HTTP cases and the `ExtensionRunner` handler-order pipeline test run in CI without skips; missing SDK fails loudly. No live login, account data or credentials are included.

## Owner-attended Codex live probe (not run here)

With the owner-provisioned `PAD_DAYBREAK_ACCOUNT` environment variable, `node scripts/daybreak_blue_live_check.mjs --live --account <owner-account>` resolves the dedicated Codex home from `$PI_HOME/agent/codex-accounts.v1.json` (`pad.codex-accounts.v1`, as in #199). The mapped canonical path must be `$PI_HOME/agent/codex-accounts/<owner-account>`; no separate Pi login folder is involved. An optional explicit `--codex-home ABSOLUTE_PATH` must match that mapping exactly. It refuses missing mapping, missing dedicated Codex login or a shared Pi/Codex home (exit 2). It checks only login-file metadata, never reads auth contents. Once provisioned and owner-approved, it resolves the Codex binary to an absolute executable and launches ephemeral read-only `codex --ask-for-approval never exec` with fixed `the configured model` and `--cyber-access-program daybreak_blue`, sends one tool-free sentinel prompt, and verifies the exact sentinel response. A response establishes only that the Codex CLI request completed, **not** that the backend granted Daybreak or that Pi's hook worked; wire-level entitlement requires separately approved observation. The script is not packaged, and was not run live in this PR. Pi's `openai-codex` provider instead reads `options.apiKey` supplied by Pi's own authentication path (`pi-ai/dist/api/openai-codex-responses.js`, stream lines 170–177); setting `CODEX_HOME` does not bind Pi to the dedicated Codex login. Never use shared Pi auth as a substitute.
