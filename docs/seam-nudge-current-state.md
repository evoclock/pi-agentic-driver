## Recovery safety findings after the audit

A local, **rejected and unpushed** `feat/recovery-journey-ledger` experiment is review evidence, not integration code to extend. Its first version acted despite a failed requested-evidence write, recorded an unsent replacement brief, invented session/board authorization, lacked a durable unknown-delivery lock, altered receipt behavior, and did not establish SAFE extraction or frozen posture. Narrow local fixes addressed prewrite refusal and unattestable handoffs, but did not make the branch an approved recovery implementation. Begin further implementation fresh from current main.

The owner accepted a specific fail-closed rule: an evidence-backed recovery action **must not start** if its requested entry cannot be persisted. If terminal persistence fails after an attempted action, delivery is ambiguous: retain the identity lock; do not automatically resend. Exact action/brief evidence must remain retrievable; a short receipt may carry an untruncated mandatory ID/size/hash reference. A digest must never stand in for authorization.

The authorization gap was discovered **after** the dated audit. The design says recovery stays within the original, source-specific dispatch authority. In current code, session tasks are mutable session working memory and their capture is observation, not owner approval. The trusted board has its own owner-confirmed promotion, verified card/claim, and assignment envelope; board claiming and session journey execution are currently separate paths. Do **not** assume that every session task must become a board card, that board promotion authorizes every journey, or that the session task digest is an approval. There is no approved general bridge or second recovery-admission store. Determine the existing authority actually available for each journey source, and refuse recovery when that source cannot prove a frozen scope and posture.
