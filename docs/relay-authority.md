# Relayed authority

A relayed approval records the owner's exact answer, the question it answered, channel, source message and time. A record attests that a configured relayer recorded those words; the hash chain does **not** prove the speaker's identity. The coordinator can check `[relay:v1 ledger=<id> relayer=<name>]` with the read-only `agentic_relay_check_request` tool against the profile ledger, never against claims in prompt prose. A covered result is only a preflight; each effect still checks its own approval at its action boundary. Without a valid record, the native confirmation path remains in force.

The active profile holds `config/relay-authority.v1.json` and `approvals/{approvals.v1.jsonl,head.v1.json,uses.v1.jsonl}`. The committed `config/relay-authority.v1.example.json` is a template, not a trusted live list. Only the owner edits trusted relayers, channels and `githubOwner`. The example leaves `githubOwner` unset; registration refuses to proceed until the owner configures the real value in the local active profile. The relay CLI takes a JSON input file and profile path; it validates a relayer against the active config before appending. The relaying bot runs the writer CLI outside a guarded Pi session: the Pi shell guard blocks direct approval-ledger access, including this CLI. The writer lock uses exclusive creation and reclaims a lock only after its age exceeds one minute and its PID is demonstrably gone. The head file records count and last hash; a missing final line is detected. A malicious writer able to replace both ledger and head can still rewrite history: no signing key is used.

Tier 0 covers reads and drafts. Tier 1 permits approved private review-branch work, registered-repo spawns and tracked-file removals in reviewable feature-branch commits within approved paths. Tier 2 permits registry additions only after automatic clone, origin and private-visibility verification. Tier 3 remains owner-direct for merges unless separately allowed by merge policy, public publication, force-push, credentials, unrecoverable deletion, registry removals and edits to trusted authority files. Standing approvals expire after seven days by default. A covered spawn skips the native dialog even if the owner is present. Tier 1 tracked-file removal is a documented scope rule, not a mechanical `git rm` path check: the current shell guard permits `git rm` without checking the approved paths. The coordinator continues loading the published npm driver, not this checkout; deployment is a separate owner action.

An authority failure should include `status: needs-owner`, the tier, missing scope, a relayable phrase and next step. A use reservation precedes the spawn mutation and counts toward `maxUses`; a partial attempt is not automatically retried. The write guard rejects direct agent-shell access to approvals paths (including reads) and invocation of the relay writer CLI; use `agentic_relay_check_request` for read-only authority checks. It is not filesystem isolation: an arbitrary program with profile write access can bypass it. Live headless acceptance remains separate from fixture tests.
