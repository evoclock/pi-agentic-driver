# Skill usage evaluation evidence and next step

For scoring skill use after a session, `skill-usage-eval` batches approved Pi transcripts and compares labelled cases. The separate agent-evals repository performs live per-session Langfuse tracing; this scorer does not trace a running session. Missing reads, unresolved paths and unlabelled cases remain uncertainty, not verified skill use.

## Daily dual-provider workflow

From the installed package root, run `node scripts/skill_usage_eval.mjs --dual --since 24h --out "$HOME/.local/share/skill-usage" --label-sample 20`. Use `--since 7d` for a longer window. The default acting verdict is Jev; the decisions API is shadow only. Set `--acting openai` explicitly to change which verdict acts. Both score the same eligible task segments, and a segment with a failed provider is excluded from both reports. No fallback silently promotes the shadow result. `--sessions DIR` selects an approved local Pi JSONL root (repeatable); `--sessions -` reads stdin. `--limit N` spreads selection over eligible files.

External bot and External bot each call this **same non-interactive workflow step** from their scheduler or command runner: invoke `node <installed-package>/scripts/skill_usage_eval.mjs --dual --since 24h --out <private-output-dir> --label-sample 20`, use the CLI's key-file loading with no key prefix, parse the single JSON stdout record, and treat exit 1 as a failed step. The caller must approve the transcript-sharing boundary before scheduling. No agent prompt, UI, or hidden confirmation is required. Run only one writer per output directory at a time so the accumulated running numbers reflect the prior history.

The stdout contract is `pad.skill-usage-dual.v1`: `startedAt` (UTC ISO timestamp), `since` (duration), `acting`, `shadow`, `output` (new absolute run directory), `sessions`, `segments`, `skipped`, `failures`, `counts` (null without labels), `readObservations` (`unresolvedReads` and `externalReads` integer counts, zero for clean sessions), and `running`. `running.providers.{jev,openai}` has `tp`, `fp`, `fn`, `tn`, `n`, `precision`, and `recall` (Wilson 95% interval or null when undefined). `running.clearWinner` is a provider name or null. Running counts retain only the latest labelled judgment per case across all runs, not the number of invocations. A case is the session header `id` (or file path when absent), segment index and catalog skill key. `running.providers` describes all latest labelled cases; `running.verifiedProviders` counts only cases with a verified header ID. `running.descriptiveOnly.cases` counts ID-less and legacy cases whose originating session cannot be verified. Renaming or copying an ID-less transcript can increase descriptive counts, but never independent sample size. `running.sessions` counts only distinct verified header IDs, including across transcript revisions. Earlier records without stable case keys remain in append-only history but cannot enter these totals. Earlier cases without a provenance flag remain in history and are descriptive only; history is never rewritten. A clear winner requires 100 unique verified cases **from 100 distinct header-ID sessions** (at most one labelled case per session), at least 20 positive labels, and non-overlapping 95% Wilson intervals for both precision and recall. Wilson intervals assume independent observations; multiple skills or tasks in one session can be correlated, so they can inform descriptive counts but cannot produce a clear winner. This conservative rule is not a paired significance test or a causal claim. Exit 0 emits one `pad.skill-usage-dual.v1` JSON record on stdout with `status: "ok"` after history append; exit 1 emits one `pad.skill-usage-dual-error.v1` JSON record with `status: "failed"` and `error` on stderr (no success stdout). A failed provider on every segment prevents any paired result and exits 1 without a history append. stdout contains only read counts, never read paths, credentials or transcript text. The private `verdict.json` and `shadow.json` retain `unresolvedReads` (`index`, `segmentIndex`, `path`, `reason`) and `externalReads` (`index`, `segmentIndex`, `path`, `realPath`) arrays, including observations on excluded failed segments; `run.json` mirrors the safe count record. A failure can leave an unindexed run directory; inspect it rather than overwriting it.

Each invocation creates a distinct timestamped directory (collisions get numeric suffixes) containing `run.json`, `verdict.json`, `shadow.json`, and optionally `label-sample.json`, `predictions.json`, `score.json`. The parent `running.jsonl` is append-only. Files use private permissions. Neither the original session nor earlier runs are modified. `label-sample.json` omits provider identities and predictions. A human labels its `cases` independently as `pad.skill-usage-labels.v1` (`rubric` plus `cases` containing the copied `id`, `skill`, `pack`, `evidenceKey` and a `needed` boolean), saves that file separately, then repeats the same session selection with `--labels <file>` and the same `--label-sample N`. An existing binding key with group or other permissions is not changed; the run record's `warnings` array flags permissions more permissive than 0600. Restrict key access before sharing samples. The HMAC-SHA-256 evidence key binds the full transcript, segment, skill metadata, displayed goal and both provider predictions. Its random private key lives in `label-binding.key` in the output root (mode 0600), outside the sample. Never provide this key, `predictions.json`, or the full run directory to the labeller. Losing the key prevents scoring labels from that output root. A streamed session must have a nonempty header `id` because stdin has no stable file path. If any input or prediction changes, the rerun rejects the labels rather than attributing them to another case. Preserve the first sample and its associated predictions as frozen evidence. To score a moving window reliably, point `--sessions` at an unchanged, approved snapshot and reuse the same catalog and providers; do not use a fresh `--since 24h` window for a later human label. If the providers are nondeterministic, rerunning can fail the binding; in that case no score is published, and the sample must be relabelled against the new evidence. The run scores against the existing #143 handcheck scorer. `predictions.json` contains both providers and is **not blind**; do not open it while labeling. Repeated runs produce new predictions and new records, never edit prior records. The scorer's required before/after slots both contain the current dual-pass predictions; these are not a longitudinal improvement claim.

The packaged Pi skill `skills/skill-usage-eval/SKILL.md` is the Pi entry point; call it manually or from a Pi scheduler. For macOS launchd, copy `config/skill-usage-daily.plist.example` to a private LaunchAgents location, set the package and output paths, and load it from your own account. For Linux, use this cron example after replacing the absolute package path: `0 2 * * * node /absolute/package/scripts/skill_usage_eval.mjs --dual --since 24h --out <private-output-dir> --label-sample 20`. Keep key files readable only by the account; neither scheduler should log its environment. Install the schedule only after deciding which sessions can be sent to both services.


## Skill-load path resolution

A skill load is a successful dedicated read whose real file matches the catalog file's real path. Filesystem resolution preserves directory links followed by `..`; only when resolution fails does the normalized path match the catalog file lexically. A relative read is resolved against the session header's absolute `cwd`, not the evaluator's working directory. A relative read with no recorded origin does not count. Shell mentions and writes do not count.

The additive `unresolvedReads` JSON array contains `{index, path, reason}` for successful read results whose path cannot be resolved at evaluation time, including broken links and missing or inaccessible files. `index` is the selected session index; `path` is the uncollapsed absolute read path; `reason` is the filesystem error code or `UNKNOWN`. These reads can still match lexically. The additive `externalReads` array contains `{index, path, realPath}` when a linked read resolves outside the recorded session `cwd`. Such reads are flagged with their real target, including non-catalog targets; they still count as a skill when that target is a catalog file. Without a recorded `cwd`, the outside-cwd flag is not inferred. The Markdown report counts both arrays. The v1 JSON fields and scoring semantics otherwise remain unchanged. Resolution is based on the current filesystem, so moved or removed historical targets are marked unresolved rather than inferred from the transcript. The handcheck scores task need, not loads. The shared scorer ships as `scripts/skill_usage_score.mjs`; the repository-only `scripts/skill_usage_handcheck.mjs` CLI, its fixtures and documentation remain excluded from the package.

## API references

The official [Decisions guide](https://developers.openai.com/api/docs/guides/decisions) sections **How decisions work**, **Choose a question type**, and **Evaluate a conversation** specify `POST /v1/decisions`, the supported model, ordered input, named predicate questions and probability answers. The **What's new** section states the 400-question request limit; this implementation uses batches of 100. The guide's **Check an image for visible damage** example includes the response array and refusal case. At runtime, nonempty `OPENAI_API_KEY` and `TYPESAFE_API_KEY` values take precedence and bypass the store. Otherwise the CLI captures a key privately from macOS Keychain or Linux libsecret. Service and account names come from `secrets.openai` and `secrets.typesafe` in the local `pad-user.v1` config, never from repository defaults. If names, tool or item are missing, only an explicitly set `OPENAI_API_KEY_FILE` or `TYPESAFE_API_KEY_FILE` permits a file fallback. The file is trimmed; a warning names the variable, not the path or value. No usable source, including an empty or unreadable explicit file, stops the run with a public reason. Implicit `<OWNER_HOME>/.openai_key` and `<OWNER_HOME>/.typesafe_key` files are never opened; their presence produces an ignored-file warning. Tool stdout stays in memory, and tool stderr and underlying file errors never enter diagnostics. The daily/External bot command has no key prefix or shell key-loading wrapper.

The config lookup order is `PAD_USER_CONFIG`, then `XDG_CONFIG_HOME/pad/user.v1.json`, then `<OWNER_HOME>/.config/pad/user.v1.json`. Missing files use defaults with no configured store names; invalid or unreadable config fails closed unless a nonempty explicit API-key-file fallback is set. Copy the structure from `config/pad-user.v1.example.json` into a private local config and replace placeholders such as `<OPENAI_KEYCHAIN_SERVICE>` and `<OPENAI_KEYCHAIN_ACCOUNT>` there. Do not store secret values in that file. The shared loader validates all section keys, including runner selection, model policy and bounded progress/attempt settings. Scheduler jobs must use that config and must not dump their environment. Tests inject a fake fetch and never contact either provider.

## Scheduled jobs

Linux libsecret's `secret-tool` needs the account's session bus. Scheduled jobs must provide `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR`; only those two variables are forwarded to the tool. A systemd user service normally has them; a plain cron job usually does not. Set them from the active session, not from guessed defaults. Keychain lookups from launchd agents need the account's login session. Tool failure does not unlock a store or start a session automatically.

Linux executable lookup ignores PATH and tries regular executable files in this order: `/usr/bin/secret-tool`, `/usr/local/bin/secret-tool`, then `<OWNER_HOME>/.nix-profile/bin/secret-tool` using the supplied HOME. Missing tools report the attempted paths without tool output.

## Migrate an existing key file

1. Locate the existing `~/.<name>_key` privately. Do not print its value or put it in shell arguments or history.
2. Create an OS-store item with placeholder names replaced locally. On macOS, run `security add-generic-password -s <OPENAI_KEYCHAIN_SERVICE> -a <OPENAI_KEYCHAIN_ACCOUNT> -w` and enter the existing value at the prompt. On Linux, run `secret-tool store --label=<LABEL> service <OPENAI_KEYCHAIN_SERVICE> account <OPENAI_KEYCHAIN_ACCOUNT>` and supply the existing value through stdin or the prompt. Do not add the value to either command.
3. Put only the service/account names in `secrets.openai` in `<USER_CONFIG>` (`pad-user.v1`). For TypeSafe, use `secrets.typesafe` and its corresponding service/account names. Never put values in the config.
4. Unset the corresponding API-key and API-key-file environment variables, then verify with `node scripts/skill_usage_eval.mjs --sessions <APPROVED_SESSION_DIR> --limit 1 --out <PRIVATE_OUTPUT_DIR>`. For TypeSafe, add `--jev`; without it this single-provider command verifies OpenAI instead. Approve transcript sharing before this CLI check; require success without a file-fallback warning.
5. Only after verification succeeds, delete the old file with `rm -- <LEGACY_KEY_FILE>`. If verification fails, retain it privately and fix the store/session setup first.

A valid config and a store hit still win over an explicit file. Broken or unreadable config cannot block a nonempty explicit `OPENAI_API_KEY_FILE` or `TYPESAFE_API_KEY_FILE`; the fallback retains its variable-only warning. Without an explicit file, broken config still fails closed.

## Follow-up: lossless transcript compaction

Use the shared parser and state fitter to preserve human and assistant messages verbatim. Pin the first and newest six transcript entries. For each older paired tool call/result ask whether the call and the full result are still needed. Keep the full result when its probability is at least 0.7. Otherwise keep the call with a short result note when the call probability is at least 0.7, or drop the paired call and result. Never orphan a result. If fitting fails, the provider refuses, or the reduction is under 25%, retain the unmodified transcript or use the host's established summary. This consumer is not implemented here. The statechart's failure terminal is the checked counterpart for no-fit or ask failure, but it does not yet model the separate compaction consumer.
