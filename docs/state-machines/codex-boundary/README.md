# Bounded Codex guard and acknowledgement models

## Safety boundary

The guard's checked promise is: no accepted command in the finite grammar in guard-model.v1.json directly selects a Codex executable or an opaque launcher. The model combines every search head with every safe or unsafe path, appends every executable option to every safe search, and includes explicit interpreter and Git configuration launch routes. A safe search has one literal query and one non-expanding path. Unsafe input must be refused by classifyBashCommand, not executed. The named RR5 counterexamples are generated as failing-decision traces and must be refused. The grammar, not an arbitrary shell interpreter, is the checked surface.

This is NOT a proof that no accepted arbitrary bash command can launch Codex. An unseen script, a build rule, a shell function, or an alias can hide executable effects from any text classifier. Even node --test can run arbitrary code. Account binding must be checked at the guarded spawn boundary and by an external host control, not inferred from this regex model. Keep this limitation visible; do not weaken the requested property by silently treating unknown shell text as safe.

| Decision | Allowed | Refused |
|---|---|---|
| Literal search | one supported command, the literal query, and a single non-expanding path | expansion, glob, extra token, executable option or substitution |
| Git log search | exact literal query | a config override or any executable option |
| Shell and Git configuration | none in the bounded opaque-launcher grammar | script interpreter, ripgrep preprocessor, Git external command, CODEX_HOME assignment |
| Git launch keys | `git config --get` reads; GIT_PAGER or PAGER of cat, less, more or empty | each exec-capable key in gitLaunchKeys (any case) crossed with every gitConfigForms shape: -c after -C or --no-pager, --config-env, config, config set, -f/--file, --local |
| Environment launchers | none | GIT_CONFIG_*, GIT_EXTERNAL_DIFF, GIT_SSH(_COMMAND), GIT_ASKPASS, GIT_EDITOR, GIT_SEQUENCE_EDITOR, GIT_PROXY_COMMAND, GIT_EXEC_PATH, SSH_ASKPASS, a non-trivial GIT_PAGER or PAGER, RIPGREP_CONFIG_PATH |
| Script operands | sh, bash or zsh with -c (the payload stays textually checked) or as plain words in another command | a shell in command position given any script operand, and . or source in command position |

## Outside the bounded grammar

The outsideGrammar list in guard-model.v1.json records known accepted commands that can still run a program the guard cannot see: direct script paths (./x.sh, scripts/x.sh), interpreters and build runners (python3 x.py, node x.mjs, make, npm run), shell -c payloads that call a script, PATH-resolved helpers (rg -z), a variable command word (x=rg; $x ... --pre=./x.sh), and command-word obfuscation (ANSI-C quoting, globs, parameter or command substitution that assembles codex). Covering them would need new model axes: command-word resolution (path, glob, quoting and expansion), interpreter-with-file, and inherited environment such as PATH. A text classifier cannot decide those axes soundly. Guarded spawn and host controls remain the account boundary.

## Acknowledgement state

AckHandoff.tla abstracts one blocking exchange and the dispatch decision that can send another prompt. Before the prompt returns, the adapter may refuse with no sent claim. A failed prompt invocation is unknown. After a returned acknowledgement, every refusal must say a prompt was sent and mark it unattributed. It enumerates nine post-prompt refusal modes (missing, unsupported, empty or switched kind; invalid or blocked status; failed or timed-out read; missing report), four pre-prompt refusals (first or second Codex observation, a kind change between the two observations, failed snapshot), and four uncertain prompt outcomes (transport failure; a stalled prompt whose recovery saw an advanced idle role, an unproven state, or a failed read-back). DispatchReprompt models runWorkerJourney's unresponsive branch: it may send one more prompt after an unresponsive result, never after a returned acknowledgement. The exchange itself never retries. TLC checks TypeOK, PostSentMarked, PreRefusalHonest, UnknownMarked, NoReplay and NoRepromptAfterReturn. Tests derive their trace lists from the FailureModes, PreModes, UncertainModes and UnresponsiveReasons sets in this TLA+ source. They assert one expected code per mode, with an otherwise valid fake report, and drive only fake Herdr process responses. Re-prompting after an unknown delivery is the existing AJ-4 autonomous design. <OWNER_NAME> accepted it on 15 Nov; the DispatchReprompt action and implementation remain unchanged.

TLC proves only the bounded acknowledgement state machine. BinaryIdentity.tla adds the bounded R5-3 executable-identity decision. The owner-configured exact binaryRealPath remains an optional version-specific target. Alternatively, binaryRealRoot plus an exact binaryLaunchPath allows a stable alias to point to any one release directory/bin/codex strictly below the canonical root; a new release does not require editing a versioned path. Dot-dot spellings, root escapes and arbitrary aliases do not count. A bare argv0 name, an unexpected path or an executable script cannot certify a spawn. BinaryIdentity.cfg checks TypeOK and OnlyAllowedCodexBinary; BinaryIdentity-unsafe.cfg replaces the identity check with a name-only decision and must violate the latter invariant. The binaryIdentityCases in guard-model.v1.json enumerate those synthetic traces separately from the shell-text grammar. The generated tests replay modeled decisions without running binaries or reading any real account homes. This is still not a live PID or tamper-proof executable identity check: process argv may not contain the absolute path, and a mutable executable can be replaced between observation and use. Such observations refuse or remain unverified rather than claiming live readiness.
