# Test behavior, not implementation

Adapted from Lauren Tan's `principle-test-behavior-not-implementation` at `cursor/plugins@99743e9c151c8537cbbf1f98bb38f34ef3368453` (MIT). Read `../how/WORKFLOW_BOUNDARIES.md`. A test is a claim about what a **caller, end user or external service** can observe: return values, error types, state read back and effects such as sent requests, rows or messages. Internal helper order, private data and collaborator choice are not user behavior unless the accepted contract makes them observable. This skill does not authorize a new harness, mock service, runtime effect or deletion of a safety test.

Challenge each test with **two imagined changes**. First break the promised behavior: a wrong value, missing external effect or duplicate effect. Would this test fail? Reject loose assertions, expected values generated by the same code under test, restated constants/prompt text that never exercise the reader, and checks on only test-built data. Next change only internal structure while keeping the same observable result. Would this test still pass? If not, it is coupled to implementation. Keep tests that detect the first and tolerate the second; propose rewriting the others, or delete only with explicit scope and proof their contract coverage remains.

Drive the approved user/caller interface with concrete input and an **independent** expected value from the requirement. Assert exactly what that contract promises: an empty list can be exact for no matches but hollow for a “some result” requirement; error type matters when callers branch on it, while exact error wording matters only if users depend on that wording. A no-charge rule can be tested by **no external payment call**, paired with a valid-charge case proving the seam can detect a call. Payload received by an external mock is observable service behavior; a call to a private helper is not. Domain invariants, such as matching keys in two tables or a compile-time type constraint, can be behavior when they are the promised contract. A mock must model the actual boundary rather than report a self-asserted success.

Under an authorized test seam, observe a red result for a known wrong-behavior case and a green result for correct behavior; check that an equivalent internal rewrite would not change the contract assertion. If the executable seam or independent oracle is absent, label those checks `unrun`; prose inspection cannot certify the test catches a bug. A passing unit test also does not substitute for a separately required real packaged/user journey.

- **Positive BDD:** Given an approved behavior contract and callable test seam, when Pi supplies concrete input, an independent expected result, a behavioral fault and a behavior-preserving internal rewrite, then the test fails for the fault and passes for the equivalent rewrite while checking the external/contracted effect.
- **Refusal BDD:** Given only internal-call assertions, a self-derived oracle, a hollow mock, missing effect grant or no executable red-capable seam, when a test is called proof of user behavior, then mark that claim `blocked`/`unrun`, preserve any load-bearing existing test until replacement proof and do not claim a fixture is a live journey.

Skill discovery is not a red/green test run or actual Pi session loading.
