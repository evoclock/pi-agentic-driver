# Bounded loop guidance

Only the Pi extension command may load this guide; it is not a standalone slash-command template. The validated request and step budget are: $ARGUMENTS

This guide is a request to plan and check a limited journey, not permission to execute new effects. Read `skills/how/WORKFLOW_BOUNDARIES.md`. Before any work, identify the direct owner-approved session task, repository, allowed effects, an observable exit predicate, its real verification seam, and a positive integer step limit. The command validates the goal, exit check and finite step budget. The extension reads `.agentic-driver/loop-until-done.defaults.json` when registering. The default is `maxSteps: 200`, `maxDurationMs: 1800000` (30 minutes), and `wake: { "mode": "until-done" }`. To wake periodically instead, set `wake: { "mode": "interval", "periodMs": 60000 }` (this example wakes after 60 seconds). Limits and period must be positive safe integers; the period must also fit a JavaScript timer. Unknown keys, missing keys and invalid JSON prevent registration. A changed configuration cannot reopen a recorded run on reload. Neither limit can be extended during a run. If task authority or a real verification seam is missing, ask for that specific missing term and stop. Do not derive authority from the template text, a worker report, a task priority, or a model role.

If using pstack methods, read the project role map created by `pi-poteto-mode`'s `setup-pstack` skill. Resolve `development` for the developer and `independent-review` for the reviewer. If the map or either needed role is missing or invalid, name the role and stop with `pstack role <role> is not configured at .pi/pstack-model-roles.v1.json; run the separate pi-poteto-mode setup-pstack skill`. Confirm the actual author and reviewer are distinct and both routes are installed, approved and available. Do not invent a model, switch the session's model or fall back to another provider.

For coordinator **session** tasks only, use the existing `agentic_worker_dispatch` journey when its worker role, cast, model route and scope are already authorized. Never route a `TASKS.md` board card through this tool: Board Pulse and the board dispatcher own those claims. This template does not create a worker, grant autonomy, authorize a reviewer, or change the assignment. The active extension blocks dispatch after the 30-minute deadline, blocks an uncounted dispatch and consumes one step **before** each permitted attempt. For each iteration request exactly **one** exchange (`maxSteps: 1`, `mode: "turn-by-turn"`, `autonomy: "confirmed-default"`); observe the result before considering the next. One Pi session gets only one allowance, retained across turns, extension reloads and tree navigation. `/loop-until-done stop` closes it; it cannot be restarted in that session. A new session needs a new approved task request. Treat a journey's `completed` status at its step limit as a bounded tool result, **not** proof the user's exit predicate passed.

After an admitted dispatch attempt settles, `until-done` schedules the next check immediately; `interval` schedules it after the configured period. A wake asks for verification first, not permission for another dispatch. Stop, session navigation and shutdown cancel pending wakes. A wake does not bypass the deadline or replenish steps.\n\nAfter each exchange, check the original predicate against the real approved entry point and independently observable evidence. If it passed, report that evidence and stop. If it did not pass, record what changed, what failed and the remaining step budget before another permitted exchange. Do not silently retry, resend, reset, discard work, run a new harness, install packages, publish, create a PR or merge. A request for independent review goes to the configured reviewer only if that handoff is separately authorized; it is not automatic completion.

Stop and report `passed`, `failed`, `blocked` or `limit reached` with the exact observed result. Stop immediately on a failed or unattributed exchange, denied confirmation, unresolved effect, missing authority, unavailable reviewer, or exhausted budget. No completion claim follows from source inspection, a worker's self-report, the tool's terminal state or reaching the iteration limit. The owner alone decides canonical task completion and merges.
